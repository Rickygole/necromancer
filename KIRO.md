# How Kiro fits into this project

This file is a plain account of what the `.kiro` directory contains and how it was produced. Judges should read it before trusting anything under `.kiro`.

## What is in `.kiro`

- `steering/`: six always-included steering docs (product, tech, structure, COBOL semantics, test integrity, no floats).
- `specs/`: requirements, design and tasks for three features (`uicalc-twin`, `diff-harness`, `workbench-ui`).
- `agents/`: three custom agent definitions (COBOL analyst, migration engineer, failure analyst) with scoped write paths.
- `hooks/`: two hook files (re-derive properties on spec or legacy source edits, and a test guard for the oracle, evidence and decisions).
- `settings/mcp.json`: registers the local oracle MCP server in `oracle_mcp/`.

## How these files were produced

These files were written as plain files alongside the code, not generated by walking through the Kiro IDE spec workflow. The specs were written by hand from the same rules table the twin was built from. The hook files were written to match the hook format and have not been confirmed through the Kiro hook panel. The custom agents have not been run inside Kiro, so `evidence/analysis/` and `evidence/classes/` do not exist yet.

## What the oracle MCP server does

`oracle_mcp/server.py` exposes four tools: compile a COBOL file inside the repo, run a batch through the compiled oracle, parse a record into fields, and compile and run a small COBOL snippet as a probe. It runs over stdio only and should never be exposed over a network, because a probe compiles arbitrary COBOL.
